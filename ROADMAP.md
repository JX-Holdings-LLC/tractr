# Tractr roadmap

A creator should be able to ship a multi-season village farming RPG or an alien greenhouse economy from the same 2D engine. The village tests whether the genre systems work together for a full game. The greenhouse tests whether a creator actually owns the rules, art and interface. A small custom minigame in each tests the boundary between the editor and code.

## Where creators can start today

The baseline is **0.13.0**. Creators can already paint and link maps, import Tiled and LDtk scenes, import Aseprite clips and audio, layer characters, animate tools and skin fonts, panels, slots and HUD icons. They can author crops, animals, machines, shops, fishing, mines, combat, schedules, relationships, festivals and quests. Dialogue supports branches, conditions and translations. Cutscenes support actors, camera, choices, audio, animation and skip behavior. Content tables, bulk edits, test states and a command-line balancing lab already exist. [Creator guide](docs/CREATOR-GUIDE.md) · [Authoring at scale](docs/AUTHORING-AT-SCALE.md)

A game no longer has to be a farm. A project chooses whether it has farming, stamina, sleep and combat, and what the end of a day and of the player's energy do. It can declare its own numbers for the player, for each scene or for each placed machine, with bounds, hourly drain and recovery, threshold effects and HUD meters. [Rules](docs/CREATOR-GUIDE.md#rules-games-that-are-not-farms) · [Properties](docs/CREATOR-GUIDE.md#properties) · [Pressure Works example](docs/examples/pressure-works)

Creators can ship JavaScript project scripts and sandboxed content packs. Code can read state, define conditions and outcomes, create entities and timers, display widget-based screens, and run minigames. The editor ships on macOS as well as Windows and Linux. **Game exports** cover Windows, Linux/Steam Deck and a web demo. Open tracker tickets overlap recent releases, so check each ticket's remaining acceptance criteria before scheduling it. [Release history](CHANGELOG.md) · [Plugin API](docs/PLUGINS.md) · [Export guide](docs/EXPORT.md) · [Full-game tracker](https://github.com/JX-Holdings-LLC/tractr/issues/224)

## 1. What creators could not trust, and how it was fixed

The five problems the 0.12 review found are fixed in 0.13.0. Each has a regression test that plays the scenario that exposed it. The checks ran on Linux: the engine suites under a virtual display and software Vulkan, the editor suites headless. Windows, macOS and browser builds were outside this hands-on check, as before.

| Problem | What a creator gets now | Where it is checked |
|---|---|---|
| A scripted morning reward was lost by continuing from the day's autosave. | What scripts and plugins answer to a new day is applied as that day starts, and anything still queued is applied before a save is written. The reward is in the autosave, once, however often it is loaded. [Timing](docs/PLUGINS.md#timing) | Quit and Continue from the day-two autosave against an uninterrupted game: [player tests](crates/farm-player/tests/player.rs), [session tests](crates/farm-player/tests/session.rs). |
| The headless replay ran different rules from the game: scripts were not loaded. | `farm-player --headless` runs the same session as the window and Play Mode, with the cartridge's scripts and plugins attached, and lists their errors. Games without plugins replay hash for hash. [Checking a game](docs/PLAYER.md#checking-a-game-with---headless) | The same scripted morning replayed, saved, loaded and continued: [headless runner](crates/farm-player/src/headless.rs). Golden replays are unchanged. |
| Problems said a recipe "can never be made" when a script gave its ingredient. | A project script that names an item or quest id counts as its source, reported once as code Problems cannot follow. A data-only game keeps its warning, and a script that does not name the item gets the warning with how to declare it. | [Graph tests](tests/FarmEngine.Authoring.Tests/UpkeepTests.fs). |
| A kept playtest became the opening of the exported game. | **Keep changes** keeps the playtest beside the opening. New Game and exports start as authored, the next playtest goes on from the kept one, and making it the opening is an explicit step with a preview in Settings. Export Game and `farmc export` say what New Game starts with. [The opening](docs/CREATOR-GUIDE.md#the-opening-and-a-kept-playtest) | Author, keep a day-40 playtest, compile: [cartridge tests](tests/FarmEngine.Authoring.Tests/CartridgeTests.fs), [editor tests](tests/Tractr.App.Tests/Game/WorkspaceTests.cs). |
| Starting buildings had no Edit Mode preview, and Goals and Mail pushed the toolbar to a second row at 1280×800. | A starter barn is drawn in Edit Mode on the tiles it stands on in play. The top bar stays on one row at 1280×800 with both features, and the pause menu offers Goals and Mail, so a gamepad reaches every action at any text size. | [Footprint test](crates/farm-render/src/shell.rs), [toolbar screenshot](fixtures/player/hud-goals-mail-1280x800.png), [gamepad test](crates/farm-player/tests/player.rs). |

Two limits remain. A project whose opening an earlier version already played into still carries that progress: Settings and the export report show it, and the creator resets it by hand. Problems recognizes a scripted source by the id written in the script's text, so an id assembled in code still needs to be written out once.

## 2. Milestones and release gates

The order reflects dependencies. Work on assets and narrative tools can proceed alongside simulation changes once the project format and regression examples are agreed. Milestone A is delivered; B–F are proposed. Pressure Works is the first small greenhouse example: expand it, and start the village beside it, as features land. The gates below are proposed release criteria.

| Milestone | What to build and why | How a creator proves it works |
|---|---|---|
| **A. Make the rules belong to the project** (delivered in 0.13.0) | Date rollover, recovery, collapse and where the player wakes are separate choices. Farming, stamina, sleep and combat are each selectable, and a game without sleep runs its clock round the day. Typed player, scene and machine properties have units, bounds, hourly rates and threshold effects, and work with the existing variable conditions and outcomes, saves and the HUD. | Done with [Pressure Works](docs/examples/pressure-works): a workshop with no forced bedtime, two greenhouses with independent pressure, a player with oxygen beside stamina. Its replays cross midnight and reload mid-shift, and run on every change. Projects without rules keep their state hashes. Still open: per-instance properties for buildings and NPCs, property-aware content tables, and labels for the generated rule and property forms. |
| **B. Give crafting the depth farming already has** | Extend exact-item recipes with tagged alternatives, catalysts, fuel, quality transfer, shared unlock conditions and persistent queues. Add reusable interactive behaviors with instance-local state. Connect outputs to shops, orders, tool upgrades and relationships so production can sustain a whole campaign. | One recipe accepts two kinds of ore, retains the forge tool, consumes fuel and transfers quality. Queue jobs in two furnaces, fill the output inventory, save and reload. Each machine resumes its own job and quantities balance. |
| **C. Give creators ownership of every visible surface** | Build on existing importers and skins with a searchable asset/reference browser, batch replacement, missing-art reports and preview of reimports. Add an editable layout and data bindings for built-in screens, starting with inventory, hotbar, crafting, shop and dialogue. Include slot groups, focus order, tooltips and text scaling. Extend replacement coverage to terrain, crop stages, people, portraits, tools, item icons, buildings, effects, pointers, title art, fonts and audio. | Reskin one project as a space settlement. Reimport a taller character and an animated crop without breaking references. Replace the backpack with a controller-navigable cargo grid and a custom detail pane. Audit the exported game for stock art, text or sounds the creator did not choose. |
| **D. Direct stories and scenes at production scale** | Keep script and form editing. Add a linked dialogue graph and scene timeline with a stage preview, camera tracks, actor blocking and audio cues. Show callers, unreachable branches and the conditions behind each choice. Let a writer jump to a named test state and preview a translation in context. | Stage a festival across two maps. A relationship and a quest change its dialogue and ending. Play, skip and replay every branch, verify rewards occur once, and check long translated text, portrait changes, actor positions and camera framing in the exported scene. |
| **E. Make unusual mechanics easy to add and explain** | Package the existing typed API, project scripts, screens and minigame hooks into a create/run/test workflow with runnable examples and source-linked errors. Add deterministic decision hooks before weather, growth, price and depletion take effect. Specify ordering, conflicts and fallback. Add a no-code trace for event conditions, queued jobs and state changes. The existing weather notification arrives after the night has applied its effects. | A plugin author builds a pollination minigame using custom art, scoring and an inventory reward. A second extension changes a storm before it waters crops. A designer binds both in the editor, sees why a trigger failed, and gets the same results after reload, replay and export. [Hook timing](docs/PLUGINS.md#timing) |
| **F. Prove a full game can ship and survive updates** | Maintain two playable reference projects, named late-game test states and old release saves. Use the existing balancing lab and progression graph to check economies and quest gates. Expand item/scene migration coverage to NPCs, crops, quests and extension-owned state. Profile saves and large frames on target hardware. | Play from a blank save through a full village year with seasons, crops, animals, upgrades, mining/fishing, marriage or another relationship arc, and a festival payoff. Complete a production chain on the alien planet, including a scripted minigame. Export both, update each with renamed content, then resume old saves with their inventory, story and machine state intact. |

Milestone A implements [system selection](https://github.com/JX-Holdings-LLC/tractr/issues/243) and [environmental properties](https://github.com/JX-Holdings-LLC/tractr/issues/244); check their acceptance criteria before closing them. Open design work covers [reusable behaviors](https://github.com/JX-Holdings-LLC/tractr/issues/245), [crafting rules](https://github.com/JX-Holdings-LLC/tractr/issues/246), [rule replacement](https://github.com/JX-Holdings-LLC/tractr/issues/247) and [runtime debugging](https://github.com/JX-Holdings-LLC/tractr/issues/248).

### Measure whether development gets quicker

Give a first-time creator the Starter Farm, a sprite sheet and a written recipe. Ask them to add an animated crop, process its harvest, have a villager request the result, and export a playable build. Record elapsed time, manual edits outside the editor and points where they need help on 0.13.0. Repeat with new creators after milestones B–E. For a developer, repeat the exercise with a custom minigame that grants the reward. Use those observed times to set release targets. Shipping a feature only helps if creators can find and use it.

### Shipping and longer-term work

- **Accessibility and distribution.** Carry forward controller rebinding, broader font coverage and right-to-left text, editor and guide localization, Windows signing, Mac notarization, macOS game export, Steamworks and configurable web demo endings. Test the actual exported packages with keyboard and controller.
- **Performance.** Measure save stalls against the existing 1 ms simulation-thread budget. Move save I/O off that thread and check interrupted writes. Profile large UI frames before adding upscaling, unchanged-frame reuse and GPU effects. Compare CPU and GPU output, including editor Play Mode.
- **After the single-player gates.** Player-installed mods need discoverability, compatibility and recovery when a mod is removed. Local and online co-op need separate player state, shared-inventory conflict handling and replay coverage for extensions. Revisit console export with a platform partner and a target game. Track interned cartridge content, authored units, condition-language work and generated bindings as enabling engineering. [Architecture](docs/dev/ARCHITECTURE.md#future-not-built) · [Console export discussion](https://github.com/JX-Holdings-LLC/tractr/issues/202)

## 3. Engine comparison for a 2D farming and crafting game

“Built in” means a creator gets the workflow with the engine. Teams using a general engine can build these capabilities or adopt third-party packages. The final Tractr row is a target assessed by the release gates above.

| Engine | Farm, craft and social simulation | Art, inventory and UI | Dialogue and scenes | Custom code and principal trade-off |
|---|---|---|---|---|
| **Tractr 0.13.0** | Built-in crops, animals, crafting, machines, schedules, romance, quests and festivals. Farming, stamina, sleep and combat are selectable, and a project declares its own bounded resources. Production still assumes exact-item recipes. | Aseprite, Tiled/LDtk, layered people, custom assets and UI skins. Built-in inventory layout choices are limited. | Branching scripts, localized text, linked maps and step-based cutscenes. | JavaScript project scripts, pack plugins, screens, entities and minigames, replayed headless with the game's own code. Hook timing before the night's effects constrains some mechanics. |
| **Godot** | Team builds or adopts the simulation, content schema and save model. | Tilemaps, animation, Control nodes and themes give direct layout control. | Scene composition and AnimationPlayer are built in. The team chooses dialogue and quest tooling. | GDScript, C# and native extensions give broad control. The team owns the integration. [Godot documentation](https://docs.godotengine.org/en/stable/) |
| **Unity** | Team integrates its own systems or third-party farming and narrative packages. | 2D tilemaps, sprites, animation and UI frameworks support bespoke screens. | Scene editor, Timeline and Cinemachine support staging. Writers need a dialogue workflow. | C#, packages and editor tooling support highly custom systems. The team maintains the connections among packages, content and saves. [Unity manual](https://docs.unity3d.com/Manual/) |
| **GameMaker** | Objects and events support a custom simulation. The team supplies seasonal, relationship and crafting rules. | Sprite and room editors suit 2D worlds. The team designs inventory and HUD behavior. | Rooms and Sequences support staging. Branching narrative and quest data need project tooling. | GML and extensions suit bespoke 2D mechanics. Large content sets need authoring tools or imports. [GameMaker manual](https://manual.gamemaker.io/) |
| **MonoGame** | Code-first framework. The team owns the simulation, persistence and content tools. | Content pipeline, rendering and input primitives let developers define every screen. | Team supplies a map editor, dialogue editor and scene playback or integrates external tools. | C# gives control over the game loop. This is the framework used by Stardew Valley and has the largest tooling burden in this comparison. [MonoGame showcase](https://monogame.net/showcase/) |
| **Tractr after milestones A–F** | Configurable systems, environmental resources, flexible production and two completed reference games. | Replaceable presentation plus editable built-in layouts, custom bindings and accessible navigation. | Writer scripts, linked graph, staged scene preview and branch tests share one story model. | A creator can add a minigame, custom screen or simulation rule and verify it in the exported game. The specialization is 2D farming and crafting. |

The first delivery is done: the lost morning reward, the scripted replay and the clean export start are fixed, and the rules and properties a greenhouse game needs are in. Next, grow Pressure Works into one alien greenhouse played from imported art through harvest, refining, sale and reload. It is small enough to finish and forces the crafting depth of milestone B, the assets and UI of C and the extension API of E to work together before the team commits to a year's worth of content.
